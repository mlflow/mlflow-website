LLM judges help you evaluate answers, compare prompts, and catch regressions. Every judgment also adds another model call. As your project grows, the cost and time spent judging become a headache.

[Jev](https://typesafe.ai/blog/introducing-system-one-models-and-jev), TypeSafe's model for structured decisions, is a candidate for these checks. We first compared Jev with **GPT-5.6, Claude, and DeepSeek** on human-labeled technical QA examples. After OpenAI released its [Decisions API](https://developers.openai.com/api/docs/guides/decisions), we ran it on the same frozen examples. We measured agreement with human labels, latency, and estimated cost.

Can Jev distinguish correct MLflow answers from answers containing factual or API errors, and how does it compare with these LLM judges?

## 1. What is Jev?

Jev is a unique model that does not generate text. A conventional LLM generates its verdict token by token. Jev, by contrast, produces only structured outputs from a fixed set of options, along with decision probabilities. TypeSafe calls it a _System One_ model, borrowing the term from Daniel Kahneman's _Thinking, Fast and Slow_ for decisions made quickly rather than through deliberate reasoning. This narrower interface lets Jev respond with much lower latency, at the cost of general text generation. See [TypeSafe's launch post](https://typesafe.ai/blog/introducing-system-one-models-and-jev) for details.

For example, give Jev a question about an MLflow API, a candidate answer, and the relevant documentation, then ask whether the answer is factually and technically correct using a question. Jev's [Noul question type](https://docs.typesafe.ai/primitives/noul) returns the probability of "yes," which your code can turn into a pass or fail. It also supports selecting a category with **Choice** and grading against ordered rubric levels with **Score**.

## 2. Why Jev is a candidate for judging

Many evaluations need a small decision about a large input. Does an answer use the right API? Does it respect the version in the user's question? Does an instruction contradict the supplied documentation?

These tasks fit Jev's interface. You can also ask several independent questions about the same state in one request. Its [published price](https://docs.typesafe.ai/models) is $0.042 per million input tokens, with no charge for output tokens. That gives us a reason to test it for frequently repeated checks.

Jev returns a classification and probability without a written rationale. A text-generating judge can provide a reason when you need to investigate a decision.

## 3. Define an LLM judge with Jev

We'll test Jev with the following LLM judge prompt: **is the answer factually and technically correct?** Starting with [MLflow 3.17.0](https://mlflow.org/releases/3.17.0/), you can use Jev directly with `make_judge` through the `typesafe:/` model URI. The [TypeSafe judge integration](https://mlflow.org/docs/latest/genai/eval-monitor/scorers/llm-judge/custom-judges/typesafe/) supports Boolean and finite-category assessments and records decision probabilities in feedback metadata.

MLflow also supports [automatic tracing of TypeSafe SDK calls](https://mlflow.org/docs/latest/genai/tracing/integrations/listing/typesafe/) with `mlflow.typesafe.autolog()` and [Jev endpoints in AI Gateway](https://mlflow.org/docs/latest/genai/governance/ai-gateway/endpoints/model-providers/#typesafe) for centrally managed credentials and usage tracking.

Install the packages and start an MLflow server:

```bash
uv add "mlflow>=3.17.0" typesafe-sdk
uv run mlflow server --host 127.0.0.1 --port 5000
```

In the terminal where you'll run Python, configure the connection and your TypeSafe API key:

```bash
export MLFLOW_TRACKING_URI="http://127.0.0.1:5000"
export TYPESAFE_API_KEY="your-typesafe-api-key"
```

Then define the judge with `make_judge`. Pin the model version to match the benchmark; use `typesafe:/jev-latest` to try the latest Jev model.

```python
import mlflow
from mlflow.genai.judges import make_judge

mlflow.set_experiment("jev-judge-comparison")
jev_correctness = make_judge(
    name="jev_correctness",
    model="typesafe:/jev-1.13.0",
    instructions=(
        "Is the candidate answer in {{ outputs }} factually and technically correct "
        "for the question and MLflow documentation in {{ inputs }}, respecting any "
        "version specified in the question? Answer yes or no. "
        "Answer yes if there is no material factual or API error. "
        "Answer no if at least one claim or instruction is materially wrong or misleading. "
        "Do not penalize style or harmless omissions. An omission is material when it "
        "makes the requested technical answer misleading."
    ),
    feedback_value_type=bool,
)
```

`jev_correctness` evaluates the candidate answer in `outputs` using the question and documentation in `inputs`. MLflow records a Boolean assessment and the probability under `typesafe.probability` in feedback metadata, using a threshold of 0.5. The benchmark below used direct TypeSafe SDK calls with separate latency and cost instrumentation; this example uses the same model version but adapts the prompt for `make_judge`, so results may differ.

## 4. Measure initial quality, cost, and latency

We created **30 MLflow QA examples** covering tracing, evaluation, prompts, datasets, and assessments. Each contains a question, a candidate answer, and an excerpt from the official MLflow documentation. A human reviewer labeled 15 answers Correct, 14 Incorrect, and one Unclear after a label correction. We excluded the Unclear example before scoring, leaving **29 comparable decisions** for every judge.

**Correction to the original table:** It showed agreement out of 30, but QA-018 had an Unclear human label and was excluded from the scored calls. We also corrected QA-016's human label after checking the documentation and rescored the saved judge outputs without making new provider calls. The table and chart below use the 29 eligible cases.

Here is one of the incorrect answers for example:

```python
data = [
    {
        "inputs": {
            "question": (
                'My `@scorer` function is called `check_answer`, but it returns '
                '`Feedback(name="answer_quality", value=True)`. '
                'Which name appears as the metric?'
            ),
            "context": (
                "1. If the scorer returns one or more `Feedback` objects, then "
                "`Feedback.name` fields take precedence, if specified.\n"
                "2. For primitive return values or unnamed `Feedback`s, the "
                "function name (for the `@scorer` decorator) or the `Scorer.name` "
                "field (for the `Scorer` class) are used."
            ),
        },
        "outputs": (
            "The metric is named `check_answer`, because decorated scorers "
            "always use the Python function name. To show `answer_quality` "
            "in the results, rename the function to that name."
        ),
        # This field is not passed to the Jev judge.
        "expectations": {"human_correctness": "incorrect"},
    }
]
```

```python
mlflow.genai.evaluate(data=data, scorers=[jev_correctness])
```

We also tested GPT-5.6 Terra and Luna, Claude Sonnet 4.6, Claude Opus 4.8, and DeepSeek-V4.1-Flash (`deepseek-flash`) on the same inputs and substantive correctness criterion. We disabled extended reasoning and limited output to 128 tokens for these text-generating judges.

On October 8, 2026, we added OpenAI Decisions with `gpt-6-luna`. We sent the same question, documentation, and answer as JSON input to `POST /v1/decisions`, with one predicate question using Jev's exact criterion. A probability of at least 0.5 counted as Correct. This was a direct Decisions API call; MLflow's `make_judge(model="openai:/gpt-6-luna")` currently uses Chat Completions and does not return this probability.

OpenAI Decisions accepted one incorrect answer: QA-002 claims that a scorer's function name overrides an explicit `Feedback.name`. Its probability that the answer was correct was **0.79**. All 29 scored OpenAI calls completed. Jev, Terra, and Luna made identical decisions on all 29 examples. Jev had the lowest estimated cost in these runs; OpenAI Decisions had the lowest observed median latency. Sonnet rejected one correct answer and accepted two incorrect answers. Opus rejected a correct answer about session and tracing metadata. DeepSeek and Sonnet both accepted an incorrect answer about span outputs.

We timed each synchronous SDK call, including the network round trip, with one worker and no retries. The table excludes one preflight call per judge. OpenAI reported 13,311 input tokens and no output tokens across the 29 scored calls. At the [Decisions API price of $0.10 per million input tokens](https://developers.openai.com/api/docs/guides/decisions#pricing-and-availability), the estimated scored cost was $0.0013311. Its 30 requests, including preflight, cost an estimated $0.0013694. These are usage-based estimates, not reconciled bills. Service conditions and network paths can change between the September and October runs, so the latency figures describe these requests rather than a general speed ranking.

## 5. Decide when to use Jev and when to defer

For this dataset, Jev matched the human labels on all 29 scored answers at the lowest estimated cost, while OpenAI Decisions was faster in its later run and missed one incorrect answer. Before adopting either judge, collect real answers from your application and inspect the errors that matter there. Both APIs return probabilities that you can use to send uncertain cases to another evaluator, but this pilot did not test a routing threshold.

Jev's lack of a written rationale matters when you are debugging an answer. You can send flagged cases to a text-generating judge for an explanation, then review both verdicts. For high-volume monitoring, measure whether the speed and cost of a decision-only judge help enough to justify that extra step.

A binary Noul question also cannot abstain. When abstention matters, use a Choice question with an explicit `unsure` option, then route those cases to another judge or a human reviewer.

## 6. Try it on your evaluation dataset

Start with a criterion you already use, label a small set of answers, and run Jev alongside your current judge in MLflow. Inspect the disagreements as well as the cost and latency. Then test your choice on fresh examples before changing the evaluator that catches your regressions.
